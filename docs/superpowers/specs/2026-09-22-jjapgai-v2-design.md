## 2. 탄 단계 상쇄

모든 탄에 `tier` 필드를 추가한다. 상쇄는 **최솟값 차감**이다.

```js
const m = Math.min(p.tier, e.tier);
p.tier -= m;  e.tier -= m;
if (e.tier <= 0) { 적탄 제거; game.score += 10; }
if (p.tier <= 0) { 내 탄 제거; }
```

같은 단계면 둘 다 소멸, 다르면 낮은 쪽만 소멸하고 높은 쪽은 단계가 깎인다.

| 탄 | tier |
|---|---|
| 염주(텐가이 주) · 부적(코요리 주) | 1 |
| 창(하가네 주) | 2 |
| 봉황 · 대형 창 (차지) | 3 |
| 물의 정령 유도구 (코요리 차지) | 2 |
| 일반 적탄 (`ONI` · `KARAKURI`) | **2** |
| 보스 일반 공격 | 2 |
| 보스 최종 페이즈 · 카라쿠리 대불 레이저 | 3 |

**적탄 tier는 스테이지 난이도로 스케일하지 않는다.** tier가 올라가면 후반에 상쇄가 무의미해져 시스템 자체가 죽는다. 후반 난이도는 탄의 **수와 속도**로만 올린다.

일반 적탄을 tier 1이 아니라 **2**로 둔 이유: tier 1이면 파워 4에서 초당 36발의 염주가 탄막을 거의 전부 지워 게임이 무력화된다. tier 2는 염주 2발을 요구한다. 이 표 하나만 고치면 난이도를 조절할 수 있도록 격리한다.

비용은 `O(내 탄 × 적 탄)`이다. 최악 20×40 = 800회/프레임 = 48k회/초로 JS에서 무시할 수준이므로 **공간 분할을 넣지 않는다**(YAGNI).

부수 변경: v1의 `ebullets` 원소에 크기 필드가 없다(`EB_W` 전역 사용). `overlaps()`를 쓰려면 생성 시 `w`/`h`를 넣어야 한다.

## 3. 캐릭터 3명 — 데이터 테이블

`CHARS[i] = { name, spr, familiar, fireInterval, main(), charge() }`, `player.char` 가 인덱스.

대안을 검토했다. 캐릭터별 함수 3세트는 발사·렌더·차지 로직이 3중 복제되어 리뷰 루브릭이 Important로 잡는 "동일 로직 블록의 중복"이 된다. 클래스/프로토타입은 상태가 `player` 하나뿐인 단일 파일 vanilla에 과하다.

| 캐릭터 | 주 무장 | 차지 | 사역마 |
|---|---|---|---|
| **텐가이** (v1의 `MONK` 재사용) | 염주 정면 P스트림 (v1 그대로, 간격 0.11s) | 봉황 관통 tier3 dmg8 | 매 (`HAWK`) |
| **코요리** | 부적 3방향 확산, 간격 0.13s, dmg1 tier1 | 물의 정령 유도구 tier2 dmg6, 가장 가까운 적 추적 | 물의 정령 (`SPIRIT`) |
| **하가네** | 창 1줄, 간격 0.20s, dmg2 tier2 | 대형 관통 창 tier3 dmg12 | 창 (`SPEAR`) |

사역마는 v1 규칙대로 **파워 2 이상에서만** 표시된다.

### 신규 스프라이트 (전부 기계 검증 통과)

셀 3px. 행 길이와 팔레트 문자 유효성을 검증했다.

| 이름 | 셀 | 픽셀 | 사용 색 |
|---|---|---|---|
| `KOYORI` | 12×12 | 36×36 | `D G N S V` |
| `HAGANE` | 12×12 | 36×36 | `C D G M` |
| `SPIRIT` | 7×5 | 21×15 | `D L` |
| `SPEAR` | 7×5 | 21×15 | `D G M` |

팔레트 3색 추가: `N = #E8E2D8`(무녀 흰 상의), `V = #B83A3A`(주홍 하카마), `L = #5A8FB8`(물의 정령). 하가네는 기존 `M`·`C`·`G`만으로 그려져 추가가 없다.

세 캐릭터의 실루엣이 구분된다: 채워진 셀 수가 `MONK` / `KOYORI` 72 / `HAGANE` 86이고, `HAGANE`는 **두 다리가 분리**되어 기계임이 즉시 읽힌다.

## 4. 30 스테이지 = 3막 × 10

| 막 | 스테이지 | 테마 | 주력 적 | 배경 |
|---|---|---|---|---|
| 1 | 1~9, **보스 10** | 요괴의 숲 | `ONI` 중심 | 짙은 녹청 |
| 2 | 11~19, **보스 20** | 증기 성곽 | `KARAKURI` 중심 | 회갈 (v1 색) |
| 3 | 21~29, **보스 30** | 천계의 화구 | 혼합·고밀도 | 붉은 하늘 |

막이 3개인 것과 보스가 3종인 것이 맞물린다 — 각 막의 끝이 그 막의 보스다.

배경은 막마다 `sky` / `far` / `wall` / `wallTop` 4색을 오버라이드한다. 도형과 패럴랙스 배율(0.25 / 0.6 / 1.0)은 v1 그대로 쓴다.

### 웨이브 패턴 라이브러리 (손으로 쓴 27개 테이블을 대체)

일반 스테이지가 **27개**다. 스테이지당 9줄 테이블을 손으로 쓰면 243줄의 반복 데이터가 되고 대부분이 무의미한 변형이 된다. 유지도 불가능하고 난이도 곡선도 통제되지 않는다.

패턴 8종을 정의하고 각 스테이지가 풀을 셔플해 뽑는다.

| 패턴 | 편대 |
|---|---|
| `line` | 일렬 횡대 |
| `sine` | 사인 웨이브 종대 |
| `pincer` | 위아래 동시 협공 |
| `vee` | V자 편대 |
| `column` | 종렬 밀집 |
| `sweep` | 화면 높이를 쓸며 순차 진입 |
| `pair` | 중형 2기 |
| `swarm` | 소형 다수 고속 |

```js
function buildStage(s) {                 // s = 1..30, 보스 스테이지는 호출하지 않음
  const act = Math.ceil(s / 10);
  const n = 3 + (s % 3);                 // 패턴 3~5개
  return shuffle([...PATTERNS]).slice(0, n)
    .map((p, i) => makeWave(p, act, s, 1.0 + i * 4.0));
}
```

각 패턴의 **정확한 좌표·마리 수·간격은 구현 계획에서 확정한다.** 본 문서는 패턴의 이름과 편대 성격까지만 정의한다 — 8종 × 3막의 구체 수치를 spec에 넣으면 설계 의도가 수치 더미에 묻힌다.

막이 결정하는 것은 **적 종류 구성**이다:

| 막 | `makeWave` 가 쓰는 적 |
|---|---|
| 1 | `oni` 만. 단 `pair` 패턴은 `karakuri` (1막에서 중형을 처음 보여주는 자리) |
| 2 | `karakuri` 중심. `swarm` · `sine` 은 `oni` (고속 소형이 필요한 패턴) |
| 3 | 패턴별로 `oni` / `karakuri` 를 번갈아 — 같은 스테이지에 두 종류가 섞인다 |

부수 효과로 **원작의 "1~4면 무작위 순서"가 더 잘 살아난다.** 스테이지 3개를 셔플하는 대신 매 스테이지의 편대 구성이 매번 달라지므로, 30 스테이지를 두 번 플레이해도 같은 순서가 나오지 않는다.

### 난이도 곡선 — 스테이지 번호 하나에서 파생

| 배율 | 공식 | s=1 | s=29 |
|---|---|---|---|
| 적 HP | `1 + (s−1) × 0.08` | 1.00× | 3.24× |
| 적 발사 간격 | `1 / (1 + (s−1) × 0.03)` | 1.00× | 0.54× |
| 적 이동 속도 | `1 + (s−1) × 0.02` | 1.00× | 1.56× |

HP 배율은 `Math.ceil` 로 정수화한다. 적 점수는 스케일하지 않는다 — 난이도 스케일링만으로 충분하고, 점수까지 곱하면 후반 스테이지가 전반을 무의미하게 만든다.

스테이지당 패턴 3~5개 × 4초 간격 ≈ **12~20초**. 일반 27 스테이지 약 7분 + 보스 3전 약 2분 = **한 판 9~10분**으로 아케이드 길이에 맞는다.

## 5. 전용 보스 3종

공통 프레임워크를 공유하고 **`attack(b, dt)` 와 `draw(b)` 만 보스별로 다르다.** HP·크기·제한시간은 테이블 값이다.

```js
const BOSSES = {
  10: { name:"오니가시라",   hp:90,  w:80, h:80,  timeLimit:0,  score:3000,
        attack: attackOnigashira, draw: drawOnigashira },
  20: { name:"카라쿠리 대불", hp:140, w:88, h:112, timeLimit:0,  score:6000,
        attack: attackDaibutsu,   draw: drawDaibutsu },
  30: { name:"텐마",         hp:200, w:96, h:120, timeLimit:45, score:12000,
        attack: attackTenma,      draw: drawTenma },
};
```

`timeLimit: 0` 은 **제한 시간 없음**을 뜻한다. `stepBoss` 는 `def.timeLimit > 0` 일 때만 타이머를 감소시키고 `BADEND` 를 판정한다.

`game.boss = { def, x, y, hp, t, phase, fireCd, dash, extra: {} }` — `extra` 는 보스별 스크래치 상태를 담는다. 보스마다 쓰는 키가 다르다:

| 보스 | `extra` 키 |
|---|---|
| 오니가시라 | `dashCd`, `summoned` (분신 1회성 플래그) |
| 카라쿠리 대불 | `laserT` (주기 내 경과), `laserY` (예고·발사 대상 y), `armCd` |
| 텐마 | `spiralAngle`, `spiralCd`, `dir` (+1 / −1) |

보스 격파 시 `game.boss = null` 이므로 `extra` 도 함께 사라진다 — 리셋 경로를 따로 두지 않는다.

### 스테이지 10 — 오니가시라 (鬼頭, 요괴 대장)

| 페이즈 | 조건 | 공격 |
|---|---|---|
| 1 | hp > 45 | 1.6초 간격 **원형 확산 12방향** (tier 2) |
| 1 | 4초 간격 | **화면 횡단 돌진** — `x` 를 200까지 0.8초에 이동 후 복귀 |
| 2 | hp ≤ 45 | 확산 **16방향**, 간격 1.2초. 페이즈 진입 시 **분신 요괴 2기 소환**(1회) |

분신은 보스 상하 `y ± 60` 위치에 일반 `ONI` 로 `enemies` 에 넣는다. 스테이지 10의 HP 배율(`1 + 9 × 0.08 = 1.72`, `ceil` → hp 6)이 적용된다 — 보스 소환이라고 예외를 두지 않는다. `extra.summoned` 플래그로 1회만 소환한다.

### 스테이지 20 — 카라쿠리 대불 (증기 대불)

| 페이즈 | 조건 | 공격 |
|---|---|---|
| 1 | hp > 70 | **조준 레이저** — 플레이어 `y` 에 2px 예고선 0.5초 → 6px 빔 0.25초 (tier 3), 주기 2.4초 |
| 1 | 1.8초 간격 | **양팔 3방향 교차탄** — 팔 위치 `y ± 30` 두 곳에서 |
| 2 | hp ≤ 70 | 레이저 **2줄 동시**(플레이어 `y` 와 `H − 플레이어 y` 대칭 위치) + 화면 하단 40px를 **증기 벽**으로 봉쇄 |

레이저는 **반드시 예고선을 먼저 그린다.** 예고 없는 전화면 즉사 공격은 회피 불가능해 불공정하다. 예고 구간(0.5초)에는 **판정이 없고** 빔 구간(0.25초)에만 있다.

증기 벽: 페이즈 2에서 0.6초마다 화면 하단(`y = H − 8`)에서 x 를 64px 간격으로 균등 분할한 위치에 tier 2 탄을 `vy = −70` 으로 올려보낸다. 플레이어를 화면 아래쪽에 머물지 못하게 하는 **지역 제한** 장치이며 회피 가능한 간격을 남긴다.

### 스테이지 30 — 텐마 (天魔, 최종보스)

| 페이즈 | 조건 | 공격 |
|---|---|---|
| 1 | hp > 133 | **부채꼴 5방향**, 간격 1.2초 |
| 2 | hp ≤ 133 | **회전 나선탄** — 0.1초마다 `spiralAngle` 과 `spiralAngle + π` 두 방향으로 1발씩, 매 발사 후 `spiralAngle += 0.35 × dir` |
| 3 | hp ≤ 66 | 플레이어 `x` 쪽으로 **압박 전진**(`x` 를 `player.x + 140` 까지 40 px/s) + 나선 **역회전**(`dir` 부호 반전) + 부채꼴 7방향 교차 |

**제한 시간 45초는 텐마에만 둔다.** 원작의 "최종보스는 시간 제한, 늦으면 배드 엔딩"은 최종보스 고유 특성이고, 10·20 보스에 붙이면 30 스테이지 진행 중 시간 압박이 세 번 반복되어 피로하다. 초과 시 `BADEND`.

## 6. 진행 보존 — 보스 스테이지 체크포인트

- 저장 키 `jjapgai.progress` → `{ act: 1 | 2 | 3 }` (해금된 최고 막)
- 보스 스테이지 클리어 시 해금: 10 클리어 → 2막 저장, 20 → 3막 저장, **30 → 저장값은 3막 그대로 두고 `CLEAR` 상태로 전이**(해금할 막이 더 없다)
- `GAMEOVER` 후 `R` → `TITLE`. 체크포인트는 유지된다
- 시작 스테이지 = `(act − 1) × 10 + 1`

**`localStorage` 는 사용 불가할 수 있다** (프라이빗 모드, `file://` 스킴, 용량 초과). 모든 접근을 `try/catch` 로 감싸고 실패 시 **메모리 폴백**으로 동작한다 — 저장이 안 될 뿐 게임은 정상 진행해야 한다. 저장 실패를 사용자에게 알리지 않는다.

## 7. 상태 기계

```
TITLE ──Z──> PLAYING(s) ──스테이지 클리어──> STAGEBANNER(0.8초) ──> PLAYING(s+1)
                  │
                  ├── s=30 텐마 격파 ──────> CLEAR
                  ├── s=30 45초 초과 ─────> BADEND
                  └── lives 0 ────────────> GAMEOVER
```

`R` 은 어느 상태에서나 **`TITLE`** 로 복귀한다 — 캐릭터를 다시 고를 수 있어야 재플레이 동기가 생긴다.

배너는 **0.8초**다. 30번 나오므로 2초로 두면 총 1분이 배너에 쓰인다.

### TITLE 화면

세 캐릭터를 나란히 그리고 `←`/`→` 로 캐릭터, `↑`/`↓` 로 **해금된 막** 선택, `Z` 로 시작. 선택된 캐릭터 아래에 무장 설명 한 줄.

## 10. 검증

v1의 하니스(`/tmp/cj/verify.js`, 포트 **8000**)를 재사용한다. 단위 테스트는 작성하지 않는다(사용자 제약 유지).

`__dbg` 에 `char`, `stage`, `act`, `cancels` 추가. 신규 훅 `__pick(charIdx, actIdx)`, `__stage(s)`.

필수 검증 항목:

1. **상쇄가 tier대로 계산되는가** — tier1 염주가 tier2 적탄을 **2발**로 지우는지, 봉황(tier3)이 적탄 3발을 먹고 소멸하는지 수치로 확인
2. **캐릭터 3명이 각각 다른 탄을 내는가** — `__pick` 후 `pbullets` 의 개수·`tier`·`dmg` 가 표에 맞는지
3. **보스 3종이 각각 다른 패턴을 내는가** — `__stage(10|20|30)` 후 `ebullets` 의 각도 분포가 확산 / 교차 / 나선으로 구분되는지
4. **레이저에 예고선이 먼저 나오는가** — 예고 구간에 데미지가 없고 빔 구간에만 있는지
5. **보스 탄이 유한 좌표인가** — v1에서 `NaN` 버그로 보스전이 무해해졌던 회귀. 전 원소 `Number.isFinite`
6. **가만히 서 있으면 세 보스 모두에게 죽는가** — v1의 진짜 회귀 테스트를 보스 3종에 각각 적용
7. **적탄이 컬링되는가** — 봄을 쓰지 **않고** 관찰해 `ebullets` 가 무한 증가하지 않는지
8. **체크포인트가 저장·복원되는가**, 그리고 **`localStorage` 를 차단한 컨텍스트에서도 게임이 정상 동작하는가**

> v1에서 배운 검증 함정: **어떤 상태를 0으로 만드는 동작 직후에 그 상태가 0인지 단정하면 아무것도 검증하지 못한다.** v1의 `boss` 시나리오가 봄을 쓴 직후 `ebullets === 0` 을 단정해 무한 누적 버그를 완전히 가렸다.
